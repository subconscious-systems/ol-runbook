# GCP production project and Docker-agent bootstrap

This Terraform root creates one production foundation: project, required APIs,
budget alerts, versioned state bucket, isolated VPC/NAT, keyless platform
service account, IAP firewall, and private Docker-agent VM. GKE, Cloud SQL,
Redis, ingress, and application secrets remain owned by the versioned
`api-gateway-infra` Application.

## Security properties

- One dedicated production project and state bucket.
- Region locked to `us-east1`.
- Bootstrap VM has no public IP and uses IAP with OS Login.
- Attached service account with `cloud-platform` scope; IAM roles authorize it.
- No service-account key, SSH metadata key, password, PAT, or Datadog key in
  Terraform.
- Uniform bucket access, public-access prevention, and object versioning.
- DNS administration granted only in the selected existing shared-zone project.
- Project and VM deletion protection enabled by default.
- Applies consume the exact plan generated by the preceding `--plan` command.

The repository `.gitignore` excludes state, tfvars, plans, generated backend
files, kubeconfigs, and common credential files.

## Prerequisites and authentication

The installing human needs project creation on the selected organization or
folder, billing-account user, budget administration, service enablement, and
project IAM administration. These are day-0 rights, not long-lived VM rights.

```bash
cd api-gateway/gcp/bootstrap
bash scripts/install-gcloud.sh
bash scripts/setup-gcloud.sh --quota-project <EXISTING_ADMIN_PROJECT>
```

Use human user/ADC login. Never create or download a service-account JSON key.

## Exact-plan installation

For a new customer installation, use the guided installer from the parent
runbook. It generates these inputs, drives both exact-plan stages, creates the
Hub resources, and runs acceptance:

```bash
bash scripts/guided-install.sh --config ../guided-install.json
```

The individual commands below are recovery/diagnostic building blocks. They
are not a second supported new-install path.

```bash
cp terraform.tfvars.example terraform.tfvars
$EDITOR terraform.tfvars

# Generate and display the exact plan.
bash scripts/bootstrap.sh --plan

# Review it, then apply that saved plan without replanning.
bash scripts/bootstrap.sh --apply
```

The apply confirmation requires the production project ID. If configuration or
credentials change, discard the old plan by running `--plan` again and review
the replacement.

Legacy multi-environment state is rejected. Destroy/archive it with the prior
runbook revision, then initialize this production-only stack with clean state.
Legacy multi-environment `terraform.tfvars` is also rejected with instructions
to recreate it from the current example; the script never rewrites local
customer inputs.

## State migration and preflight

The state bucket cannot be the backend until it exists, so the first apply is
local. Migrate immediately:

```bash
bash scripts/migrate-state.sh
terraform state list
terraform plan
bash scripts/preflight.sh
```

The post-migration plan must be empty. Keep a secured copy of the automatic
local state backup until a second authorized operator confirms the GCS state is
readable.

Preflight verifies billing, every required API, private Shielded VM posture,
OS Login, IAP/NAT, attached service account, absence of user-managed keys, and
host readiness.

## Long-lived platform service account

The `gateway-platform` account receives service-scoped administration for GKE,
networking/load balancing, Cloud SQL, Redis, Secret Manager, DNS, service
usage, and reviewed IAM bindings. It does not receive Owner or Editor.

Project IAM administration remains the highest-risk grant because the platform
creates WIF/ESO and Datadog STS bindings. Prefer a reviewed custom role or IAM
Conditions where the customer can enumerate exact release permissions.

Operators receive IAP/OS Login access, act-as permission for this one service
account, and object administration plus bucket metadata read on this one state
bucket.

## Scripts

| Script | Purpose |
| --- | --- |
| `guided-install.sh` | Run/resume the five-approval production installation |
| `install-gcloud.sh` | Install/check gcloud and GKE auth plugin |
| `setup-gcloud.sh` | Human and ADC login without service-account keys |
| `bootstrap.sh` | Generate or apply the exact production foundation plan |
| `migrate-state.sh` | Move initial local state into versioned GCS |
| `preflight.sh` | Read-only foundation checks |
| `repair-host.sh` | Reapply Docker/gcloud/kubectl host setup over IAP |
| `run-agent.sh` | Securely prompt for and install the Distr Docker target |
| `connect-k8s-agent.sh` | Securely prompt for and install the Distr Kubernetes target |
| `connect.sh` | IAP/OS Login break-glass shell |
| `rotate-app-secret.sh` | Secret Manager application-secret rotation |
| `smoke-checks.sh` | End-to-end read-only production checks |

Scripts infer project, region, zone, and VM from Terraform outputs. Connect
secrets are pasted into hidden prompts, restricted to `app.distr.sh`, and sent
over IAP stdin rather than command-line arguments.

## Teardown

Do not destroy the foundation while either Distr agent or the platform exists.
Follow [../rollback-teardown.md](../rollback-teardown.md). Before final destroy:

1. Preserve required evidence and state.
2. Set `protect_bootstrap_vms = false`, generate a plan, and apply it.
3. Move foundation state to a backend that will survive project deletion.
4. Set `project_deletion_policy = "DELETE"`, generate a plan, and apply it.
5. Generate and review the final destroy plan from the surviving backend.

Project deletion is asynchronous and has organization-level consequences.
